02: Access Control

Role-based access today.
Tuple-scoped permissions next.

Access control is live and enforced today. The next iteration, which extends scoping to brand, market, and product level, is in active build.

Current state: role-based access control
  • Organisations are isolated tenants. No cross-organisation data access is architecturally possible.
  • Users are assigned roles: View, Manage, or Approve.
  • Approve is scoped to Legal Approver role only. Marketing users cannot approve claims.
  • All access actions are logged with user ID, timestamp, and action type.
  • User de-provisioning removes access immediately.
Next iteration: tuple-scoped permissions
Users will accumulate permission tuples of the form (Role) + (Scope). A single user can hold multiple tuples, each opening a specific door. This enables brand-level, market-level, and product-level access separation within a single organisation.
In active build. Can be scoped to Reckitt onboarding timeline.
Example (next iteration): a Reckitt Dettol EMEA approver has exactly two permission tuples.
(Role: Viewer) + (Scope: Region.EMEA, Brand.All) (Role: Approver) + (Scope: Region.UK, Brand.Dettol)
This user can view all EMEA content but can only approve Dettol claims scoped to the UK. A Mead Johnson Nutrition team member in a separate scope has no visibility into Dettol content. Neither user can see the other's work. Access is enforced by architecture, not by policy alone.
SSO / SAML / SCIM
SAML 2.0 SSO and SCIM provisioning are committed for delivery at onboarding. Flourish will federate against Reckitt's IdP (Azure AD or Okta). Leaver access is revoked automatically via SCIM de-provisioning.
Access reviews and offboarding
Access reviews are performed periodically under the ISO 27001 programme. User offboarding triggers immediate revocation. All access events are logged and auditable.

04: AI Governance

Your data is yours.
It never trains a model.

The core commitment
Client Vault data (brand standards, claim libraries, product specifications, approved content) is stored in Flourish's own infrastructure. It is never used to train any AI model. All model access is routed via OpenRouter. Only enterprise API models with confirmed Zero Data Retention and zero-training terms are used. Free-tier, consumer and public models are never approved.
Which AI models does Flourish use?
Models are accessed through OpenRouter, our model gateway. Only enterprise API models with confirmed Zero Data Retention and zero-training terms are approved for use. Free-tier, consumer and public models are excluded. The approved model list is reviewed weekly.
What is sent to AI models?
Included: the content under review, task-relevant claims from the Vault, applicable regulatory rules.
Not included: PII, full Vault contents, unpublished data outside task scope.
Each agent call is stateless. Models hold no memory of prior calls.
Audit trail on every AI action. Every AI-assisted operation produces a permanent record: what was generated, which claims it referenced, which regulations applied, who reviewed it, and when. Fully traceable to primary source.
