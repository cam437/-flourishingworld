Internal Strategy Brief

Translation in Flourish

What the research says, what to build, and how to talk about it — without overstating anything a buyer can disprove.

📅 June 2026 👤 Prepared for Maddy 🔒 Internal — not for distribution
The most important finding first
Headline

On raw translation quality, specialist engines no longer reliably beat frontier LLMs. Any story that rests on "our translation is more accurate than ChatGPT's" is on thin ice.


WMT24 and WMT25 evaluations show LLM-based systems — Gemini, Claude, GPT — winning the majority of language pairs against traditional neural machine translation engines, including at document level. This closes off one narrative before it becomes a liability.

Where specialist systems still genuinely win is not quality. It's three things:

Reliability
Architecturally constrained to translate. Won't fabricate or drift in an unattended pipeline the way a general-purpose LLM can.
Latency
LLMs are 10–100× slower for bulk volume. At scale, this matters operationally.
Terminology control
Translation memory and enforced glossaries that stay consistent across thousands of strings and over time — per client, compounding.
Two angles — same answer

The CEO narrative and the CTO build converge

CEO — The narrative that sells

Flourish translates claims, not words

The market has moved decisively against "thin wrappers." VC funding in 2026 explicitly flows toward orchestration, governance, and proprietary data flywheels — and away from application veneers over someone else's model.

The line that sells: "Translation is a governed compliance event, not a language swap." A claim approved in English for the UK is not automatically substantiated when rendered into German for Germany. That crosses a regulatory boundary — and that is precisely Flourish's Operating Context and Legal Expert Agent territory. No translation vendor touches that.

CTO — The cleanest build

Adaptive translation via API — no model training

Fine-tuning your own model is off the table. It only starts beating the baseline at ~5,000 segments per direction, requires a training data pipeline, model hosting, evaluation harness, and a retraining loop per client per language pair. Wrong use of two engineers.

The modern best practice has moved past fine-tuning entirely: adaptive translation at inference time using translation memory and glossaries — no model training. Fix a production error in minutes by adding a corrected pair. The per-client asset is the translation memory, which you own and which compounds.

Build recommendation

What to integrate and why

Option Verdict Reason
Build / fine-tune own model Off the table Requires training pipeline, hosting, retraining loop per client. No headcount to carry it.
Route translation through OpenRouter Not quite right OpenRouter routes general-purpose LLMs. It doesn't expose Lara or DeepL as routable endpoints. Accurate framing: OpenRouter for LLM tasks, a separate translation API called by your orchestration logic.
DeepL Pro API Fallback Strong quality, well-understood integration. Good comparison baseline. Less purpose-built for LLM-orchestration workflows.
Lara (by Translated) Lead candidate Ships an MCP server and SDK for branded translation. Exposes translation memory management over TMX. Built to sit inside an LLM workflow rather than replace it. Maps cleanly onto how Flourish already orchestrates.

The clean build

  • Orchestration layer calls Claude / GPT for generation and reasoning
  • Calls Lara (or DeepL as fallback) for localisation at volume
  • Legal Expert Agent re-runs substantiation against the target Operating Context after translation
  • Translation memory stored per organisation as a Vault-adjacent asset — owned by Flourish, compounding over time
What to say — and what not to say

The narrative and the build must tell the same story

The multi-model point earns its place, but as evidence of judgment rather than as the headline. Claude and GPT for reasoning, a domain-specific translation model for localisation at volume, cheaper small models for classification — this demonstrates the orchestration layer is real.

The mistake would be making translation the proof point for "not a wrapper," because it's the weakest one. The strong proof point is the Vault and claim substantiation. Translation is a supporting witness, not the lead.

⚠️

The moment marketing says "better translation", engineering can't back it and a buyer can disprove it. As long as the story is "governed, consistent, claim-aware translation" — the narrative and the build tell the same true story.

When you're ready to test

The right bake-off — not "find the best AI"

Don't frame it as finding the best translation AI. Frame it as a bounded bake-off on real WeightWatchers regulated copy across 2–3 languages, scoring three things that actually differentiate:

Terminology consistency
Do brand terms, claim language, and product names stay consistent across thousands of strings and over time?
Post-editing time
How much human correction is required? This is the real cost driver.
Unattended behaviour
Does it ever fabricate or drift in a batch run without a human in the loop? This is the reliability test.

Quality will likely be close across Lara, DeepL, and a bare Claude call. Lara should win on consistency and reliability — and that result justifies the integration without overstating it.

Before you build anything

One question to ask WeightWatchers first

The "Works" tool WW mentioned is most likely a mishearing of Lara, Wordbee, or their agency's instance of Smartling.

💬

If their agency is already standardised on a specific translation engine, the cleaner integration may be to receive their translated output for compliance review — rather than translate inside Flourish at all. That changes the build materially. Pin down the exact tool name before any bake-off.
